## Architecture and authorization

`AttendanceSubmission` is a screen/authorization-owned coroutine state machine over injectable `ProofBackend` prepare/upload/finalize/receipt operations. The adapter interface is controlled by tests. **No live Supabase mutation or Storage adapter is installed or constructed in this phase.** The normal coordinator factory supplies only `DisabledProofBackend`, whose methods throw a fixed safe failure without issuing HTTP. This is an operation-level gate, not button hiding, remote configuration or a runtime enable switch.

The coordinator creates an operation only for a current approved-student attendance binding and a Fresh summary's permitted next action. It reassesses freshness first. The same binding fences user/session/client/authorization epoch. Authorization is revalidated before prepare, upload, finalization and reconciliation; ownership is checked after I/O. Existing approval withdrawal, SDK invalidation, replacement and logout cancellation paths close the operation. No second authentication session or widget data source is introduced.

`ProofSession` validates the captured image before capture acceptance and again before/after confirmation authorization. It can pass a bounded no-follow JPEG read plus a fresh monotonic GPS fix to a confirmation consumer. The consumer is awaited, concurrent confirmations are blocked, byte buffers are zeroed in finally, and files retain the existing symlink-safe cleanup behavior. Invalid images never reach the consumer. The default device-only preview behavior is preserved.

UI state exposes only phase/problem enums. It contains no SDK client, tokens, paths, bytes or coordinates. Sensitive attempt metadata stays inside the operation. Terminal non-finalization errors drop location. No new durable proof/widget storage, public URLs, logs, service-role keys, upload deletion or server proof cleanup is added.

## State machine and uncertainty

States: Ready, Preparing, Uploading, Finalizing, Completed, Failed, Cancelled, OutcomeUnknown, Disabled.

Each instance generates one stable UUID; repeated taps and subsequent submit calls cannot replace it or submit twice. There is no automatic mutation retry. Finalization dispatch is marked before I/O. Timeout, malformed receipt or unconfirmed failure after dispatch remains OutcomeUnknown. Cancellation after dispatch does not mean the server did not mutate.

Reconciliation performs a bounded authoritative receipt read for the same upload ID and unchanged coordinates. Only a validated receipt can complete; no receipt remains uncertain. It never blindly resends finalize or generates a replacement request. Success requests summary refresh through the existing attendance coordinator; widget publication remains its existing trusted derivation. A read-refresh failure does not negate a confirmed punch.

Within the authorization binding, a pending/unknown operation prevents opening another submission. Dismissal closes the screen-owned operation, clears sensitive location and cancels local work. Recovery across actual OS process death, re-login or app restart is deliberately **not** claimed: live execution must stay disabled until a secure recovery-only checkpoint and recovery UI are reviewed. The SQL supplies receipt lookup for a known upload, but not a public request-ID lookup for a lost upload ID. No unsafe automatic retry is implemented.

## Companion UI

Only approved students with Fresh attendance receive the server-derived Time In/Out verification entry. Reuses CameraX/foreground GPS, explicit proof confirmation and the existing device-only route. The attendance route plainly says submission is disabled and displays gate/progress state. Normal navigation has no fake success route or hardcoded test account. Test code uses injected controlled responses. The read-only widget remains unchanged; no widget mutation action is added.

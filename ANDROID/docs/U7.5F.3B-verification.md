## Failure-window threat model

Cancellation is never proof that a dispatched network request did not execute. All restart recovery is read-only. No state resumes prepare, upload, finalize or discard.

| Window | Durable/local evidence | Authoritative requirement and permitted recovery |
| --- | --- | --- |
| Before prepare | No record before validation; PrepareIntent committed before dispatch | A record cannot prove dispatch did or did not occur. With no upload identity, retain unresolved state. |
| Prepare dispatched, response lost | Stable owner/request/action; PrepareIntent | No exposed read-only request lookup exists. Do not replay the prepare RPC. Administrator/backend evidence is needed. |
| Prepare response received | Prepared; server-confirmed upload/session IDs | These are reservation identities, not attendance. Read matching receipt only. |
| Upload started | UploadIntent persisted before upload | Do not resend bytes. A missing receipt does not establish upload status. |
| Upload completed, acknowledgment lost | UploadIntent | Cannot distinguish unacknowledged successful upload through receipts alone; remain unresolved. |
| Upload acknowledged | Uploaded | Upload is not a punch. No automatic finalize. |
| Finalize dispatched | FinalizeIntent persisted before dispatch | Read exact owner/upload receipt; never repeat finalize. |
| Finalize committed, response lost | FinalizeIntent | Only a matching immutable receipt can establish attendance completion. |
| Receipt received | Identity/action/timestamp validation | Journal Confirmed replacement must succeed before cleanup; no success derived from local timing. |
| Confirmed completion | Confirmed until exact-CAS cleanup | Crash before cleanup still requires a new authorized receipt read. Missing evidence remains unresolved. |
| Logout during any stage | Retain encrypted evidence; invalidate binding/cancel jobs | Hide recovery immediately. A delayed result cannot publish or clean up through the withdrawn binding. |
| Account replacement | Single encrypted unresolved slot retains original owner | Different student gets a generic blocker, no identifiers and no receipt read for the previous account. |
| Approval revocation/expired session | Withdraw approved authority and recovery presentation | No new recovery reads until current authentication/profile approval has been validated again. |
| Process killed/force-stopped | Last complete atomic record; no camera/GPS recovery | Reopen after trusted authentication; perform at most one bounded read per trigger. Physical OS-kill/force-stop is not claimed as tested. |

Nothing persists selfie bytes, latitude, longitude, accuracy, proof paths, URLs, tokens, SDK clients or authorization leases. Proof capture/cache cleanup is unchanged; no background camera/location activation.

## Journal schema and secure storage

`RecoveryRecord`: schema 1, positive monotonic revision, owning UUID, stable request UUID, `time_in`/`time_out`, phase and paired nullable server-confirmed upload/session UUIDs. Session ID is necessary because the receipt binds both upload and attendance session. No proof path is needed. Intent phases encode uncertainty; local wall-clock timestamps are unnecessary and do not authorize cleanup.

The application-owned `RecoveryJournal` is the single serialization point for all production writers. A synchronized lock protects read/compare/replace and exact record/revision CAS. New attempts require an empty slot. Old revisions, owner changes, changed server identifiers and withdrawn writers are rejected. There is one application process and one journal owner; cross-process writers are not supported or introduced.

`EncryptedJournalStorage` uses AES-256-GCM, fresh randomized IVs, format version and domain-separated AAD, with a separate non-exportable Android Keystore key. Storage is under `Context.noBackupFilesDir/native-recovery/attempt.enc`; existing backup/cloud/device-transfer rules exclude private storage. No plaintext fallback or key-loss deletion exists. Corruption/schema/key-loss/storage errors retain the file and block submissions, without logging file paths or content.

Ciphertext replacement uses checked file sync/close, same-directory rename and directory sync; AtomicFile is retained only for compatible reads/legacy rollback. See the adversarial correction below. Reads are bounded to ciphertext maximum plus one sentinel before decoding (4 KiB journal plaintext bound). Platform APIs work at minSdk 26; Java 9 `InputStream.readNBytes` was intentionally avoided. Encryption and disk I/O occur off the main dispatcher. The journal lock linearizes already-entered writes; revocation guards and identity/revision CAS prevent late work from overwriting a replacement record. No multiprocess/global authentication state is added.

## State machine and submission integration

PrepareIntent -> Prepared -> UploadIntent -> Uploaded -> FinalizeIntent -> Confirmed -> exact-CAS removal. Every outbound stage is preceded by a completed journal write and a current-lease check. Storage failure prevents the next dispatch. Cancellation/errors leave the last durable phase rather than erase evidence. Definite rejection remains a failure in the existing submission presentation, but reservation uncertainty is conservatively retained because no approved read-only rejection-resolution policy exists.

The existing `AttendanceSubmission` accepts the shared journal for future approved wiring and fake verification. It keeps stable request IDs, records server identities before the next operation and writes Confirmed only after the existing strict full receipt validator. The **DisabledProofBackend** path skips journal creation because it cannot dispatch any operation; this avoids phantom unresolved attempts during today's disabled preview workflow.

The separate `AttendanceRecovery` owns recovery across Activity observers in the application's coordinator scope. Hidden/Checking/None/Unresolved/Confirmed/Unavailable presentation contains no identifiers. Duplicate active checks coalesce. Timeout or malformed/unauthorized/network results exit Checking and retain uncertainty. A recovery result does not authorize any attendance action; existing current approval plus fresh attendance still governs the action boundary.

## Account isolation and wiring

`AuthCoordinator` creates one private journal and recovery owner. Only `StudentApproved` with the accepted current SDK user/token/client/authorization binding can bind recovery. Pending, rejected, admin and signed-out accounts do not read the journal or receipts. Logout, profile withdrawal, client/session replacement and attendance AccessDenied withdraw the recovery binding and hide its presentation. The current SDK/lease is checked before and after receipt I/O; old callback tests wait for actual old work completion.

Unresolved evidence survives logout. Student B sees only a generic unresolved restriction and cannot query, display, continue or delete A's attempt. The single-slot policy intentionally blocks B's new submission too until A returns and authoritative evidence resolves the slot, or a future approved administrator recovery procedure exists. No local "discard evidence" button is supplied.

An internal journal-storage injection supports isolated coordinator tests; it cannot change the hardcoded mutation backend. Normal navigation still constructs only **DisabledProofBackend**. `SupabaseProofBackend` and `SdkProofTransport` still have no application construction site. The new `SdkRecoveryReader` exposes GET receipt reads only, using the existing coordinator client/session; it has no prepare/upload/finalize/discard method or feature flag.

## Local SQL contract and gaps

Inspected read-only:

- `DTR/supabase/migrations/20261007000100_u41_attendance_proof_foundation.sql`: private reservations uniquely bind `(student_uid,request_id)` to upload, session, action and path; all private-table privileges are revoked from authenticated clients. Public immutable receipts have unique upload ID, exact foreign-key ownership/session/action/path and approved-owner/admin SELECT RLS.
- `DTR/supabase/migrations/20261008000100_u42_attendance_proof_finalization.sql`: atomic attendance mutation + receipt insertion + reservation attachment; one official server timestamp; two starts per Manila day; one open session; overnight Time Out; idempotent finalization is not permission for Android automatic replay.

Recovery GET selects only `id,student_uid,upload_id,attendance_session_id,action_type,official_punch_at,attached_at` from `attendance_proofs`, filtered by current owner and saved upload. The parser requires zero or one row, exact selected keys/types, UUID identity/action/session match and valid ordered server timestamps. Empty results remain unresolved. No coordinates or proof paths are fetched by this reader. The existing 64 KiB production stream reader bounds success/error bodies before String/JSON decoding and closes streams; foreign-origin final responses are rejected by exact scheme/host/port comparison. A final audit tightened the initial host-only check and added an actual SDK fake-HTTP redirect regression before the final build/device verification.

Public receipts contain no request_id. The encrypted journal's server-confirmed upload/session identity, backed by SQL's unique reservation/FK, is the only available join to the original request. No lookup RPC is invented. Lost prepare responses, uncertain unfinalized uploads, receipt absence and RLS/deployment uncertainty cannot be resolved automatically. No local timeout/expiry invents failure or success. Deployed migrations/policies/receipt availability were **not** verified.

### Encryption and checked durability

AES-256-GCM, randomized per-write IV, authenticated domain/version, non-exportable Keystore key and noBackup storage remain intact. No plaintext fallback, secret logging or corruption/key-loss reset was added. Samsung tests verify distinct IVs, authenticated reopening, non-exportable key, ciphertext tampering/key loss, bounded reads and absence of other-user read/write permissions.

The production `replaceRecoveryCiphertext` helper (`EncryptedJournalStorage.kt:99`) syncs the parent directory, writes a bounded ciphertext to a NOFOLLOW temporary file, forces and closes that file, performs checked `Os.rename`, then syncs the directory. The directory descriptor uses public Android APIs, NOFOLLOW and fstat directory validation. Unsupported/failed operations fail closed. Removal also checks and syncs the directory. Temporary cleanup affects only its leaf; a pre-rename failure retains the previous committed record, and a post-rename sync failure preserves conservative new evidence. Submission storage failure blocks further submissions pending an explicit inspection. No response bodies or sensitive paths are exposed.

[AOSP AtomicFile source](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/master/core/java/android/util/AtomicFile.java) supports the original void/logging behavior; the actual Samsung probe independently reproduced unsuccessful replacement reported as success. Host tests inject file-sync, rename and directory-sync faults through the real writer helper, asserting zero backend dispatch; a pending symlink cannot truncate its target. Samsung tests also leave an interrupted `.new` file and confirm the prior complete encrypted record survives reopening. Checked successful fsync provides OS/filesystem durability guarantees, not proof of a physical power-loss experiment. Disk-full paths are modeled as write/sync failures; the device disk was not deliberately filled.

### Coordination and account isolation

`RecoveryJournal.confirmAndClear` (`RecoveryJournal.kt:69`) serializes validated authoritative confirmation and cleanup. Absence is idempotent after the same binding's confirmed cleanup; an existing record must match exact owner/request/action/upload/session and be at least the expected revision. Newer phases of that same attempt may join confirmation; a different replacement attempt cannot be erased. Both callers retain strict server receipt validation and current authorization guards. No local phase can confirm attendance.

New real-thread tests cover competing begin/advance and concurrent confirmers. A deterministic held-finalize test proves recovery cleanup and original completion can converge without overwriting success. The Samsung coordinator barrier restores approved A, holds its old HTTP read, logs A out, restores approved B, verifies B's own fresh attendance/widget projection and generic recovery restriction, then releases and joins A's old read. B remains approved, A's evidence remains intact and neither old receipt nor proof state crosses accounts. This does not claim coverage of the separately deferred blocked widget-publication replacement test.

Normal production construction remains hardcoded DisabledProofBackend at `auth/AuthCoordinator.kt:135`. The real mutation adapters have no normal construction site, no hidden enable flag was added, and recovery only performs fenced GET receipt reads. No startup mutation, automatic replay, camera/GPS restart, proof metadata in widgets or false local punch confirmation was found.

### Local SQL reconciliation assessment

The private reservation table has no authenticated read grant or exposed request-ID lookup RPC. Lost prepare responses therefore cannot be resolved by request_id alone under the inspected contract. Public receipts omit request_id but bind the journal's server-confirmed upload/session/action/owner through SQL uniqueness and foreign keys. Missing, malformed, unauthorized, ambiguous or delayed receipts preserve uncertainty; no blind retries are permitted.

The inspected Storage policy **does allow approved owners to read their reserved objects**, including discarded/expired reservations. A future validated read-only object/metadata existence contract could help distinguish uncertain upload status without Storage mutation. That reader is not implemented or deployed-tested here; object existence cannot confirm an attendance punch or authorize finalization. Current receipt-only recovery remains unresolved for uncertain unfinalized uploads. This is a future integration contract, not a claim that SQL forbids all object reads.

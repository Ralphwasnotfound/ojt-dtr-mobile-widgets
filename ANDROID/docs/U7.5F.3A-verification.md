### Prepare

`POST /rest/v1/rpc/attendance_proof_prepare`, JSON `{request_id: UUID string, action_type: "time_in" | "time_out"}`. SQL parameters are `request_id uuid, action_type text`. Exactly one array row with UUID `upload_id`, UUID `attendance_session_id`, string `photo_path`, ISO instant `expires_at`. No bucket or student_uid response field exists: ownership is checked through the exact canonical path `{authenticated_uid}/{attendance_session_id}/{upload_id}/proof`. Expiry must be later than the adapter clock. No arbitrary path/bucket is accepted.

The server reserves for one hour, locks the approved student profile and binds unique `(student_uid, request_id)`. Same pending request/action may return the same valid reservation; changed action/state/expiry or attendance state is rejected. The adapter preserves the supplied stable request ID and dispatches at most one prepare per adapter; retry policy belongs to the existing workflow and no automatic retry is introduced.

### Private upload

`POST /storage/v1/object/attendance-proofs/{reserved_path}`, raw JPEG bytes, `Content-Type: image/jpeg`, authenticated Bearer session, public client API key, `x-upsert: false`. Standard REST upload is corroborated by [official Supabase upload documentation](https://supabase.com/docs/guides/storage/uploads/standard-uploads).

SQL bucket is private, maximum 5,242,880 bytes, permits JPEG/PNG/WebP. Android remains JPEG-only; byte count and JPEG signature are checked by the adapter, while the existing capture/decoder validation remains responsible for valid images. INSERT policy requires `owner_id=auth.uid()`, approved student, exact owned pending reservation and unexpired ticket. No UPDATE policy; no overwrite, public URLs, signing URLs or service-role credentials. No new Storage dependency: the established SDK HTTP client supplies the smallest wire boundary.

Upload response is not attendance evidence. Known HTTP rejection is distinguished from timeout/transport ambiguity; neither permits automatic overwrite/resend. Finalization requires a confirmed successful upload response. Unknown upload recovery/download comparison is not implemented here and remains a live-enablement prerequisite.

### Finalize

`POST /rest/v1/rpc/attendance_proof_finalize`, JSON `{upload_id, latitude, longitude, accuracy}`. SQL types UUID/numeric/numeric/numeric. No client timestamp or user-ID parameter is sent. Coordinates must be finite, latitude [-90,90], longitude [-180,180], accuracy finite and >=0, matching SQL; the existing capture workflow retains its stricter positive-accuracy/freshness checks.

Returns one JSON composite receipt object, not a row array. The adapter validates exact owner, reservation/session/upload/path/action/coordinates, UUID receipt ID and official/attached server timestamps using ProofContract. Attached time cannot precede punch time. No success is inferred from a Storage response or invented local timestamp.

Server locks profile/reservation/session/Storage metadata, validates owned object MIME/size, uses a single `clock_timestamp()` after locks, and atomically punches and attaches proof. Time In permits first and second starts, denies third, rejects an existing open session, stale expected attendance state or changed Manila day. Time Out closes the reserved current open session, including an overnight session; it has no same-day start requirement. Attached ticket retry returns immutable receipt only with unchanged coordinates. Legacy attendance_time_in/out grants are revoked by local U4.2 migration. Adapter does not resend finalize; duplicate/overlapping calls are rejected after the first dispatch.

### Reconciliation

`GET /rest/v1/attendance_proofs?select=*&student_uid=eq.{uid}&upload_id=eq.{upload_id}` returns zero or one array row. SQL SELECT RLS permits approved owner or approved admin; adapter additionally requires its approved-student lease and exact captured SDK owner. Upload identity is tied to the prepared stable request; request_id is private and absent from the public receipt, so it cannot be directly selected/validated from this table.

Receipt validates all finalization identities and coordinates. `[]` remains no authoritative answer, never definite failure or permission to resubmit. `[null]`, nonarray, duplicate rows, malformed fields, wrong account/action/path/coordinates or timestamps are rejected. Only a dispatched finalize can reconcile. No receipt polling or another finalize is introduced.

SQL errors include 42501 approved/authentication denial, 22023 invalid request/action/location/proof, and P0001 reservation/attendance-state/conflict/proof-required errors. HTTP 401/403 maps to Authorization; 404 (including missing RPC) to Unavailable; other 4xx to Rejected; 5xx/timeout/transport failure to OutcomeUnknown. Bodies are discarded from error state. After finalize dispatch, the existing workflow conservatively retains OutcomeUnknown even for a reported server rejection; no rollback/cancellation is claimed.

## Architecture and authentication

`SupabaseProofBackend` implements the existing ProofBackend and requires explicit transport plus current coordinator lease predicate. Missing transport fails Disabled. It validates wire contracts and keeps only per-attempt reservation/action/location validation context and dispatch guards; AttendanceSubmission remains the sole business-state owner. A Mutex serializes operations, including overlapping duplicate calls, without independent background jobs/polling.

`SdkProofTransport` accepts the existing SupabaseClient and mandatory current-lease predicate. It creates no client/authentication/session manager. Captured SDK session user/token must still match the live SDK session, remain unexpired and Authenticated, and coordinator predicate must still be valid before request construction, immediately before dispatch, after HTTP and after response consumption. Adapter owner must match transport owner before any request. Production callers in a future separately approved phase must supply `{ coordinator.currentProof(capturedTicket) }` for both layers with the exact ticket-owned client: this retains user/session/client/generation/approved-state fences. There is intentionally no adapter factory in the coordinator in this phase.

Existing SDK storage fencing, secure persisted session consistency, profile revalidation and authorization-withdrawal behavior are untouched. A token refresh/replacement invalidates the captured transport; approval must be established under a new coordinator lease instead of adopting credentials implicitly. Delayed results cannot complete into a replacement owner. In-flight HTTP already dispatched cannot be undone locally; server approval/RLS remains authoritative.

Pinned Supabase 3.2.6 compiled API/bytecode was inspected: SupabaseClient.httpClient, supabaseHttpUrl, auth.currentSessionOrNull/sessionStatus, and KtorSupabaseHttpClient.request. The existing LogLevel.NONE configuration is retained. Cancellation is rethrown; no exception body/cause, proof bytes, GPS, path or token is logged or placed into presentation/widget state. ByteArray is handed to the existing HTTP client without adapter image copies or durable storage; caller's secure finally-wipe and symlink-safe cleanup remain unchanged.

AttendanceSubmission adds fixed transport-error mapping; the receipt parser distinguishes absent arrays from malformed null rows. Neither changes the disabled factory or terminal/uncertain outcome protections.

### Original Low finding and exact correction

The U7.5F.3A review found an unbounded bodyAsText call, historically at SdkProofTransport.kt:44. It could allocate an entire unexpected successful/error response before JSON validation. **That Low finding is resolved.**

Selected cap: **65,536 response bytes (64 KiB)**. The local prepare contract returns four scalar fields and the receipt contract returns one small fixed-schema record; 64 KiB provides substantial headroom while bounding allocation. This is a byte limit, not a character count or the separate 5 MiB image upload limit.

The pinned Supabase 3.2.6 prepareRequest and Ktor 3.3.1 HttpStatement/ByteReadChannel APIs and implementation bytecode were inspected. HttpStatement.execute(block) calls fetchStreamingResponse and scopes cleanup/cancellation. Using an ordinary eager request followed by a length check could already buffer the entire response, so the transport now uses **client.httpClient.prepareRequest(...).execute { response -> ... }**, then the production `readProofResponse(response.bodyAsChannel())` helper. No independent HTTP/auth client, plugin or dependency is created.

The helper allocates a single **65,537-byte** array (cap plus one sentinel), reads available bytes only into its remaining space, and rejects immediately upon receiving byte 65,537. It does not drain an oversized stream. Only bounded EOF permits UTF-8 String allocation; JSON decoding and HTTP status/error classification still occur later in the existing adapter. The helper ignores Content-Length entirely, so absent, undersized, oversized or malformed metadata cannot increase the application limit or truncate the delivered body voluntarily. Tests apply the bound to actual delivered channel bytes; they do not claim to change a real HTTP engine's protocol framing rules.

Success, non-2xx and malformed JSON bytes all use the same reader. Overflow throws fixed `ProofTransportFailure(Unavailable)` with no body/message/cause. Other stream failures become fixed OutcomeUnknown without retaining underlying exception details. CancellationException is rethrown, not classified as intentional non-execution. The existing workflow still keeps dispatched finalization OutcomeUnknown; no retry/resend or rollback claim is introduced.

The bounded byte buffer is wiped and the channel cancelled in finally on success/failure/overflow/cancellation. The request scope also cancels when ownership is withdrawn before entering the reader, and HttpStatement performs scoped raw-channel/job cleanup. No response body, proof path, token, location or image is added to logs, exception diagnostics or widget state. Existing LogLevel.NONE configuration remains. No independent all-platform log capture is claimed; tests verify payload-free diagnostics and source inspection verifies no response logging call.

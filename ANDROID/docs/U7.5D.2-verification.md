# U7.5D.2 — Attendance freshness and lifecycle

Baseline: `ab0307ba2651f9040871ec8ed533870979a5d90b`, main, expected origin; clean pre-flight.

## Policy and security

A successful read receives an in-memory monotonic observation (`SystemClock.elapsedRealtime`)
and a device-wall-clock display timestamp. Freshness lasts 120 seconds, chosen to bound
misleading data age without continuous network polling. Age expiry only marks stale;
manual refresh, foreground resume, Philippine midnight and clock-change events request reads.
The display timestamp is explicitly device time, not a server-signed confirmation time.
A server day differing from the current Manila day remains stale. Stale data never grants
an action or authorization. No persistent attendance cache exists.

Each lifecycle registration owns a unique opaque token and registers/removes its
observer and clock/date/timezone receiver. Effective foreground means at least one
registered token is resumed. Duplicate notifications are idempotent, disposal removes
only its token, and callbacks for disposed tokens are ignored. One shared timer starts
on the first foreground claim and stops only after the final claim is released.
Repeated RESUMED notifications and recomposition do not initiate duplicate reads.
Backgrounding cancels attendance reads and the foreground timer. Every foreground return
withdraws prior approval and data, revalidates the server profile, and binds/reads only
for an approved student. Offline profile revalidation remains closed and retryable.
Refreshes coalesce. A boundary during an active read queues one follow-up. Existing
client/session/user/epoch and storage-lease fences reject retired or late work.

A foreground timer wakes at freshness expiry or the next Asia/Manila midnight, never
polls in the background and does not use a service/worker. Midnight and device clock
changes invalidate freshness and request authoritative reads; open overnight sessions
are preserved rather than reset or reconstructed locally. The SQL contract remains
unchanged: complete durations come from the server and open sessions are excluded.

No tokens, SDK clients or PKCE material enter attendance state. No mutations, widgets,
proof capture, dependency upgrades, backend, Vue, iOS or hosted changes are included.

## Deferred limitations

Hosted RPC deployment and live backend behavior are not verified. Multiple-device changes
remain invisible until the next authorized read. Revocation is observed at server reads /
profile revalidation, not pushed instantly from the server. In-memory snapshots disappear
on process death; restoration revalidates. Device clock labels may be inaccurate; monotonic
age remains independent. Persistent widgets and attendance actions remain future phases.
The existing wall-clock PKCE age, custom URI ownership and accepted prior test completion
barrier findings remain deferred; this phase does not redesign those areas.


## U7.5D.2.1 ownership correction

The review found that a shared Boolean allowed one owner to cancel another owner's
timer. Per-registration claims now preserve expiry and midnight across overlapping
owners, without changing authentication/session fences or the freshness policy.
README now accurately documents foreground authorization withdrawal/revalidation.
Clock broadcasts are handled by one resumed registration, preventing duplicate
receiver callbacks from queuing redundant reads.

Deterministic unit coverage tests both owner release orders and pause/disposal,
idempotency, stale callbacks, final-owner cancellation, new registrations and midnight.
Samsung regressions use two LifecycleRegistry owners provided to the actual
CompanionNavigation: disposal preserves automatic expiry, pause preserves midnight,
an in-flight boundary queues a complete second coordinator read, replacement SDK
identity clears old attendance, and logout rejects a deliberately non-cooperative
late response while both owners are active. Internal constructor clock/wait injection
keeps these tests deterministic; production defaults remain unchanged.

## Low finding 1 — guarded image handling

Previously, BitmapFactory/EXIF/matrix work ran unguarded in composition. Missing,
unreadable or corrupt content could crash or leave captured state authoritative.

ProofFiles.readProofImage checks an actual readable nonempty file and handles only
expected IOException, SecurityException and invalid-input IllegalArgumentException.
Unexpected programming failures are not converted to a valid image. ProofImage uses
real Android JPEG decoding and ExifInterface, rejects invalid dimensions/MIME and
unsupported orientation values, and samples to at most 800 pixels per dimension.
Orientation absent/undefined uses the normal image orientation. Recoverable malformed
metadata accepted by Android's parser is not a promise of forensic EXIF validation.

A validator is required by ProofSession; production supplies ProofImage.valid.
Validation occurs before accepting capture and before and after confirmation's
suspending authorization read. Invalid content is never confirmed. Preview decode
failure rejects only the exact currently owned file, deletes it, clears location and
provides a retryable CaptureFailed message. A delayed old-preview failure cannot
invalidate a later capture. Confirmation coalesces while an operation is active.
Intermediate/validation bitmaps are recycled; the single displayed bitmap is released
on disposal. No image paths, EXIF fields or bytes are logged. FLAG_SECURE and private
cache ownership are unchanged. Capture can be retried after failure.

## Low finding 2 — deterministic cleanup and replacement

ProofSession.awaitOperations joins its actual child jobs, including caller finally
blocks after non-cooperative work. Tests no longer use yield to stand in for completion.
Controlled entered/release barriers keep late callbacks blocked across dismissal,
logout, replacement and authorization revocation; assertions follow caller completion.
The existing coordinator logout regression also now joins proof cleanup.

Coordinator-level Samsung tests use the real AuthCoordinator, pinned SDK, isolated
Keystore/session storage and MockEngine. Student A initially has location state (and
an image in the GPS case), then capture/GPS work is blocked. Logout fences A's session;
a real PKCE sign-in/callback completes for approved Student B while A remains blocked.
B starts a distinct proof session and produces distinct image bytes/accuracy/permission
state. Releasing A's late callback and awaiting caller cleanup proves A has no proof
state/files and B remains authoritative and unchanged. Additional coordinator tests
cover GPS logout and capture/GPS profile revocation. No production safeguards were
weakened, no second production auth session was introduced.

## Process-death cleanup

Existing Application.onCreate already removes native-proof on next startup and blocks
proof entry if cleanup fails. No concrete gap in that scoped startup behavior was found.
The same operation is extracted into cleanupProofCache for deterministic JVM and Android
filesystem tests. Tests remove abandoned nested proof files, preserve unrelated private
files, and repeat cleanup safely. They simulate restart inputs; no actual Samsung OS
process-kill experiment was performed. Files may remain until next startup after abrupt
process death; deletion depends on filesystem availability and is not secure erasure.

### Remaining Low finding — recursive deletion follows directory symlinks

Location: ProofFiles.kt:15 (startup); the same existing pattern appears at
ProofSession.kt:158 (screen-owned directory cleanup).

A synthetic host-JVM probe using the pinned Kotlin 2.2.21 stdlib created a directory
symlink under a temporary native-proof tree pointing to a separate temporary directory.
The exact deleteRecursively primitive returned true and deleted the unrelated sentinel.
This is verified library behavior on the host, not a Samsung symlink attack experiment.
If an unexpected directory link exists in the private proof namespace, recursive cleanup
can escape that namespace and delete unrelated same-UID files, despite the nominal path.

Non-blocking Low: proof paths are private and generated by the application with UUID
names, no reviewed writer creates links, no external path input is accepted, and ordinary
other-UID applications cannot plant such a link. No reachable external attack or existing
on-device link was demonstrated. The behavior predates this helper extraction. Minimal
follow-up: centralize a no-follow traversal for startup/session deletion, unlink symbolic
links without descending, fail closed on traversal errors, and add host/Android root and
nested-link preservation tests. A fully hostile same-UID concurrent path swap would need
stronger descriptor-relative handling and is outside the current threat boundary.

### Image/EXIF and cancellation assessment

The production decoder is wired into mandatory capture/confirmation validation and the
preview failure path. Expected I/O/security/invalid-input exceptions become rejection;
CancellationException is not caught by the guarded reader and explicit coroutine catches
rethrow intentional cancellation. Programming errors are not treated as successful proof.
Rejected images cannot be confirmed, failure deletes their owned file and allows retry;
identity-based rejection cannot delete a replacement capture. Duplicate confirm is gated
before invalid-state checks and tested with a blocked real operation. Bitmaps are sampled
and validation/intermediate allocations recycled; preview allocation is disposed on exit.

Decoding is synchronous on Main, so lifecycle/cancellation callbacks execute after that
bounded decode returns. There is no coroutine checkpoint inside BitmapFactory/EXIF work.
The existing current-lease check on preview access and confirmation still prevents stale
proof consumption; no cross-account publication defect was identified. Native decoding
and EXIF parsing are tolerant format readers, not strict JPEG/metadata integrity or
cryptographic proof validators. Severely truncated/oversized/low-memory and Compose
bitmap-disposal stress cases have no dedicated device tests. Heap exhaustion cannot be
promised recoverable by the expected-exception handling. No additional failure was
reproduced; these remain explicit limits rather than claims of exhaustive validation.

## U7.5F.2A.1 — Symlink-safe cleanup correction

This section supersedes the prior remaining Low finding and prior final scope/results.
Baseline remains 308d8ec50fd68772d0efee20f529c9b478751465 on main, matching actual
origin/main. Preflight matched the five modified/five new Android files, nothing staged.
All existing image-error and replacement-barrier hardening was preserved.

Root cause: File.deleteRecursively follows directory symlinks while walking. A lexical
native-proof path alone did not restrict traversal to owned storage; both startup and
screen cleanup used that primitive. The earlier host probe deleted an unrelated sentinel.

### Correction and ownership

ProofFiles now centralizes tree and single-image deletion. Production ownership is
anchored to the trusted Context.cacheDir and its exact native-proof namespace, not a
filename prefix. Session targets must be immediate children of that root; outside paths,
parent traversal and substituted ancestor links are rejected. ProofSession requires the
explicit cache owner, checks directory ownership before operations, and uses the same
helpers for failures, retake, confirmation and close. NativeCamera late/error/cancellation
callbacks also use the scoped image unlink helper. Screen paths remain generated UUIDs.

Directory symlinks, including a symlink at the startup namespace root, are deleted as
leaf links and never intentionally traversed. SecureDirectoryStream providers use open
parent descriptors and NOFOLLOW_LINKS for child directory opens and file attribute reads;
relative unlink/delete avoids the directory-check/open symlink race. Providers without
that capability use walkFileTree with no FOLLOW_LINKS, an additional directory-symlink
check, and ownership checks on the fixed parent path. Missing paths are already clean;
other I/O/security failures return false without logging paths. Streams close with use.

The code uses java.nio.file APIs available at the project's API-26 minimum; compile/lint
and the Samsung runtime check validate this build's actual compatibility. No dependencies
or toolchain were changed. No camera acquisition or GPS workflow was redesigned.

On cleanup failure a closed proof session remains closed, its in-memory photo/fix is
cleared, and CleanupFailed is surfaced. Startup cleanup failure still blocks proof entry.
No failed deletion establishes authorization or confirms proof. File deletion is not
secure erasure, and unavailable storage can retain private files until a successful retry.

### Sentinel and regression evidence

The repeated standalone host probe invoked the compiled production ProofFiles helper,
not a reimplementation. Results: sessionCleanupSucceeded=true,
startupCleanupSucceeded=true, unrelatedSentinelPreserved=true,
proofNamespaceRemoved=true. The host filesystem reported SecureDirectoryStream support.

Host tests use real temporary files/symlinks. Cases include normal/abandoned files,
unrelated files, links to files/directories, nested links, a namespace-root link,
missing files/directories, invalid/outside/traversal and false-prefix paths, repeated
cleanup, A-session cleanup preserving B/app files, and invalid-ownership/ancestor-link
cleanup failure leaving proof closed. Existing retryable image and async barriers remain.

Samsung ProofImageTest adds real private-cache symlink fixtures for file/directory/nested
and namespace-root links; A cleanup must preserve B and unrelated sentinel files. It also
exercises actual runtime NIO APIs. These fixtures simulate filesystem conditions, not an
actual OS process kill, real selfie or production account. No symlink test was silently
skipped. Results recorded below after device verification.

5. **Client configuration:** `ANDROID_SUPABASE_URL` and
   `ANDROID_SUPABASE_CLIENT_KEY` come from environment variables, or the ignored
   Android-only `supabase.local.properties`. Environment values take precedence.
   Build-time key validation rejects server-only/invalid material before
   BuildConfig generation; runtime validation accepts only HTTPS project origins
   and publishable/anon key types. Actual values were unavailable and were not
   invented or copied from web `.env`. Both generated config values are empty;
   the app shows a closed configuration message with sign-in disabled.

6. **Secure session persistence:** One application-owned client installs Auth and
   PostgREST. SessionManager encrypts the full SDK session snapshot (access,
   refresh/provider tokens, expiry and user metadata) in private no-backup files.
   Android Keystore creates a non-exportable AES-256 key; platform AES-GCM uses
   a fresh nonce, authenticated file/package context and versioned ciphertext.
   AtomicFile handles replacement. Corrupt ciphertext/key loss fails closed;
   there is no plaintext fallback. Logout's write fence and deletion share the
   save lock, preventing late persistence after logout. Deletion is checked.

7. **PKCE persistence:** One encrypted transaction contains its random ID,
   creation time, S256 challenge, verifier and claimed flag. Lifetime: five
   minutes. The reviewed SDK saves verifiers asynchronously, so the browser
   waits for encrypted persistence and a matching challenge. A delayed old save
   cannot populate a replacement transaction. Storage errors from that SDK
   background save do not escape as uncaught exceptions. Claim is single-use;
   success, cancellation, invalid callback, failure and expiry remove material.
   Unclaimed browser transactions survive restart; interrupted claimed exchanges
   are discarded, requiring a new sign-in.

8. **Google flow:** SDK Google provider with explicit PKCE, exact native redirect
   and `prompt=select_account`; a Custom Tab opens after the verifier is ready.
   The SDK emits the Supabase parameter spelling `code_challenge_method=s256`.
   No WebView, password collection, embedded Google secret or browser-session
   copying is used. A callback code is exchanged without automatically importing
   a session; only a current, uncancelled result is imported.

9. **Exact native callback:** `ph.edu.bsit.tcc.ojtdtr://auth/callback`.
   An authorized operator must confirm/add this URI externally in the existing
   Supabase Auth redirect allowlist. Hosted settings were not changed.

10. **Callback validation:** Exact scheme/host/raw path; no port/user-info or
    fragment; one valid code or a bounded provider-error query; no duplicate,
    token or unexpected query parameters. An active fresh unclaimed transaction
    is required. Cold and warm Activity intents delegate centrally. Unsolicited
    and duplicate callbacks cannot replace a current account. Intent callback
    data is removed after capture. Receiving an intent never grants access.

11. **Restoration/refresh:** Encrypted native session loads once through the
    application coordinator, refreshes when near expiry, verifies its user via
    Supabase Auth, then rereads its own profile. No cached role is trusted across
    launches. Cancellable application-owned operations check expiry every minute
    while the process lives; SDK autonomous refresh is disabled to keep mutations
    under the same mutex/epoch policy. No Worker is created or scheduled.

12. **Trusted profile:** Ordinary authenticated PostgREST queries only
    `public.profiles`, columns `id,role,status`, filtered to authenticated user ID.
    No writes, service-role credentials, registration/approval RPCs or Google
    user metadata determine authorization. Read failures and malformed results
    remain closed and distinct from a proven missing row.

13. **Account states:** RestoringSession, SignedOut, Authenticating, LoadingProfile,
    StudentApproved, AdminApproved, Pending, Rejected, RegistrationRequired and
    AccessUnavailable. Approved student/admin map to their confirmations; student
    pending/rejected map to corresponding states. A successful missing row plus
    verified Google identity maps to RegistrationRequired. Unsupported admin
    combinations, mismatched ID, duplicate rows, unknown role/status or malformed
    data fail closed. Future lifecycle statuses can extend ProfilePolicy after
    approval; none are introduced in production. Retryable profile/session errors
    do not become registration. All states use minimal temporary UI on Welcome.

14. **Logout:** Advances the epoch and immediately removes UI authority; cancels
    profile/exchange/refresh/expiry jobs, fences/deletes session and PKCE material,
    attempts a bounded LOCAL native sign-out, and always clears the SDK session.
    If filesystem failure blocks SDK cleanup, the closed client is discarded and
    access remains unavailable. Normal logout returns SignedOut. Remote revocation
    failure cannot preserve local authorization. Web/browser sessions stay separate.

## Exact backend mapping

Normal coordinator recovery now calls only these read RPCs, with the current SDK session and fixed JSON argument names:

- POST `/rest/v1/rpc/attendance_proof_recovery_lookup`: `request_id`, for lost prepare identity.
- POST `/rest/v1/rpc/attendance_proof_recovery_upload_status`: `request_id`, `upload_id`, once identity exists.

SQL contract version 1 exact top-level keys: contract_version, observed_at, student_uid, request_id, lookup_status, reservation, object_status, receipt_status, receipt. Exact reservation keys: upload_id, attendance_session_id, action_type, state, expires_at, expired. Exact receipt keys: id, student_uid, upload_id, attendance_session_id, action_type, official_punch_at, attached_at.

Production decoder rejects extra/missing/duplicate keys (including nested keys), incorrect primitive types/nullability, unknown version/enums, noncanonical UUIDs, identity/action mismatches, malformed timestamps, inconsistent expiry flags and contradictory receipt/reservation/status combinations. Receipt timestamps must be ordered. No path, URL, coordinates, image, token or raw diagnostic fields are accepted. SQL UNKNOWN and NOT_FOUND carry null identity/receipt; FOUND alone is never success. The decoder reuses the existing immutable receipt validator for exact owner/upload/session/action/server-time joins.

| Evidence | Behavior |
| --- | --- |
| NOT_FOUND / UNKNOWN | Retain original journal, block new submission; never abandon or replay. |
| FOUND / missing receipt | CAS-enrich a validated missing identity only; retain interrupted phase and uncertainty. |
| PRESENT / MISSING / INVALID | Catalog observation only; no attendance confirmation or mutation permission. |
| Object UNKNOWN | Retain without enrichment or phase advancement. |
| CONFIRMED receipt | Validate exact binding, CAS-enrich lost identity if needed, then same-attempt confirm-and-clear. |
| Timeout / cancellation / permission / missing RPC / network / malformed | Preserve durable evidence, remain blocked; fixed generic status, no fabricated success. |

A second explicit recovery check after identity enrichment uses upload-status; no polling, automatic mutation retry, upload or finalize is added. Valid receipt confirmation is independent of object presence, which does not prove bytes/digest/durability. Journal status never computes attendance hours or widget authority.

## SDK/session and journal boundaries

Reader captures the coordinator's SDK session and mandatory lease predicate. Before dispatch, after HTTP reading and before journal/publication it checks owner, current client/session/token/authorization generation, authenticated SDK status and expiry. Refresh/replacement invalidates the captured reader; coordinator reauthorization supplies a fresh binding. 401/403 become sanitized authorization failures. All errors preserve unresolved evidence and block submission. No service-role configuration or independent authentication session exists.

The inspected pinned Supabase 3.2.6 wrapper exposes its underlying Ktor client under SupabaseInternal. The opt-in is confined to observation(): a short-lived configured HTTP view shares that SDK engine but disables redirects before dispatch, then is closed in finally. It has no separate Auth plugin/session storage. Samsung tests prove 302/307/308 cause exactly one request and repeated observations retain the original SDK engine/session. The existing 64 KiB streaming response reader bounds successful/error/malformed bodies before String/JSON allocation, ignores untrusted Content-Length and closes/cancels streams. Cancellation propagates. No response-body exceptions or values reach diagnostics.

Encrypted journal schema 2 adds only `recovered` plus the existing paired upload/session IDs. New writes use schema 2; schema-1 records decode unchanged with recovered=false. A schema-1 lost intent is migrated lazily, atomically and encrypted on valid CAS enrichment, without silently discarding old evidence. Recovery metadata retains PrepareIntent instead of claiming acknowledgment or network progress. Recovered records cannot advance through mutation phases; only authoritative confirmation may finish them. Owner/request/action remain unchanged, revision increments, stale CAS and withdrawn bindings are rejected. Existing AES-GCM/Keystore/noBackup/fsync writer is unchanged, with no plaintext fallback. Corruption/storage failure retains conservative evidence and blocks work.

Legacy receipt-only interface fixtures and the minimal GET implementation remain for existing regression compatibility; the production SdkRecoveryReader overrides observation() and normal coordinator recovery uses the strict RPC path. There is no runtime flag or alternate production mutation factory. Normal construction remains hardcoded DisabledProofBackend in AuthCoordinator; no prepare, finalize, Storage upload/delete or hidden activation is added.

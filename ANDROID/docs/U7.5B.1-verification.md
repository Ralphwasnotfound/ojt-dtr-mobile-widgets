## Finding 1: OAuth setup timeout

Root cause: the five-second PKCE readiness timeout throws
`TimeoutCancellationException`, a `CancellationException`, so the prior general
cancellation handler rethrew it without removing the transaction or leaving
Authenticating.

The setup handler now catches timeout before intentional cancellation. It removes
only the attempt's transaction by atomically comparing its random ID, including
when cleanup finishes late. Owned deletion does not expire/delete a different
transaction as a side effect. Timeout cleanup runs in NonCancellable and publishes
AccessUnavailable(OAuth, retryable=true), or SecureStorage failure if cleanup
fails. No browser opens and no stale callback can exchange the transaction.
Retry returns to SignedOut when there is no native session. Intentional cancellation
also performs owned cleanup and rethrows cancellation; epochs still suppress stale
state publication. No TTL, clock source or callback ownership redesign was made.

## Finding 2: SDK background invalidation and session replacement

Root cause: Supabase 3.2.6 schedules session_not_found cleanup on its own authScope;
clearSession deletes shared PKCE/session storage and changes its session status.
Coordinator mutexes/epochs did not cover those jobs, and the minute refresh loop
silently skipped null sessions. Profile publication also lacked a final current
client/session identity check.

Inspected the pinned SDK's AuthImpl and SessionStatus API, including asynchronous
PKCE save, clearSession, importSession and close:
https://github.com/supabase-community/supabase-kt/blob/3.2.6/Auth/src/commonMain/kotlin/io/github/jan/supabase/auth/AuthImpl.kt
https://github.com/supabase-community/supabase-kt/blob/3.2.6/Auth/src/commonMain/kotlin/io/github/jan/supabase/auth/status/SessionStatus.kt
The cached 3.2.6 GoTrueErrorResponse implementation confirms error_code is the
server error field used by the regression fixture.

Each SDK client now receives a revocable, coordinator-owned storage lease for all
session and PKCE SDK reads/writes/deletes. Lease changes and entered storage
operations share one mutex; old cleanup delayed before entering that mutex becomes
inert after retirement. Logout immediately withdraws UI authority, advances the
epoch, cancels work/observation, retires the lease, fences/deletes native material,
then attempts bounded LOCAL revocation and closes the old SDK client. Replacement
login uses a fresh SDK client and lease; a fresh engine factory preserves this
boundary in synthetic tests as well as production. Closing an old SDK scope alone
would not protect against non-cancellable cleanup, so the storage lease is required.

The pinned SDK sessionStatus StateFlow is observed without new polling. Current
NotAuthenticated/RefreshFailure withdraws authority through the same logout path;
retired clients' emissions are ignored. A changed authorized token/user identity
also withdraws authority. Before publishing profile-derived state, the coordinator
checks the operation epoch, active client, current Authenticated status, user ID,
and the exact token identity used for validation. A null session in the existing
refresh loop now also fails closed. No new polling loop or global state is added.

## Regression coverage and verification

Four new emulator regressions use synthetic HTTP only and the real pinned SDK,
Android Keystore and isolated encrypted storage:

- Delayed PKCE verifier exceeds the real five-second readiness timeout: encrypted
  transaction disappears, browser never opens, late verifier/callback cannot
  resurrect it or exchange a code, UI exits Authenticating, retry reaches SignedOut.
- Real SDK session_not_found background deletion is deliberately delayed across
  logout and a successful different-user/admin login. Releasing old cleanup leaves
  the new SDK session, encrypted persisted identity and AdminApproved authoritative.
  Old SDK import/save cannot re-authorize or overwrite the new session. Genuine
  current-session clear immediately/fail-safely withdraws authorization and clears
  persisted material.
- Current SDK session removed during a delayed profile read cannot publish approval.
- Owned cleanup for an older PKCE transaction cannot delete a ready replacement;
  cleanup for the actual owner removes it.

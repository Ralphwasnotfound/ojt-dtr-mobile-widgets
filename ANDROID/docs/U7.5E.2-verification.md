# U7.5E.2 — Widget attendance integration

Baseline: `1df0a2f84540ca756cce153ecd1a6557fd461ef5`, main, expected mobile origin,
clean working tree. Android-only changes; no dependency or backend changes.

## Existing capability and actual integration gaps

U7.5E.1 already publishes completed/remaining hours, server-derived open-session status,
and successful fetch time from the companion's trusted coordinator. DtrApplication
observes account and attendance changes; WidgetPublication isolates instance failures
and provides bounded neutral recovery. Rendering has no independent SDK/session/RPC.
There is no reason to duplicate those pipelines or add background polling.

This phase clarifies status as Currently timed in / Not timed in, explicitly labels
unavailable authority, and identifies the successful refresh timestamp as Manila/device
clock. Completed durations remain server-provided; open-session elapsed device time
never contributes. Remaining hours retain the validated required-hours calculation.
Four projection regressions cover overnight open sessions, genuine server zero totals,
refreshing snapshots and device timezone independence.

## Freshness, refresh and security

Companion Fresh/Refreshing/Stale/Unavailable states retain their existing meaning and
120-second monotonic policy. Foreground profile revalidation, Manila midnight invalidation,
clock/timezone broadcasts and SDK fencing are unchanged. Widget snapshots are always
Stale — open app to verify, including underlying Fresh attendance: Android cannot reliably
guarantee a two-minute background redraw after suspension/process death. Missing authority
or data is Unavailable. The widget never invents zero records or claims Fresh authority.

Logout, revocation, SDK invalidation and replacement withdraw authorization; projection
checks current client/session/user/generation and approved student binding. Pending,
rejected and admin accounts receive no student aggregate. Only minimal display strings
enter widget state; no identity, token, verifier, proof, location or selfie is stored.
No persistent attendance cache was added. Taps retain the explicit native companion intent.
Existing encrypted authentication storage remains coordinator-owned.

## Successful Student A-to-B regression

The new instrumentation test uses the production AuthCoordinator, actual pinned Supabase
SDK, isolated encrypted storage and synthetic MockEngine endpoints. A restored approved
Student A receives 2h completed / 484h remaining. The production publication observer
blocks an approved A update behind a non-cooperative barrier. A logs out and the in-memory
presentation becomes neutral before release. The same coordinator performs a normal PKCE
signIn/callback/token exchange for Student B, validates B's own approved profile and reads
B's distinct 4h completed / 482h remaining summary. Persisted session identity must be B,
one exchange must occur, and PKCE material must be removed before releasing A.

After release, both injected widget hosts must hold B's presentation; no A write may occur
after the first B publication, and no additional attendance RPC may result from rendering.
This is successful replacement through production APIs, not rejection of an unsolicited
SDK import. The blocked operation may simulate an old submitted host write before B's
publication; cancellation/serialization then publishes current B authority. It does not
prove real launcher delivery order or instantaneous withdrawal of already submitted views.

## Physical and live-environment limits

The existing user-reported 8/8 Samsung launcher checks belong to U7.5E.1 and are preserved
in that document; they are not newly repeated U7.5E.2 manual checks. Automated injected-host
barriers are separate from real launcher operations. The existing recreated Application
test verifies a safe unknown/lazy-auth state; actual OS process-death recovery remains
unverified. No approved production account or live Supabase attendance was tested.

Real launcher redraw delivery/order, OS process-death recovery, live RPC deployment,
approved production widget display and live account revocation remain deferred acceptance
requirements. In-memory withdrawal is immediate; host clearing is asynchronous and may
fail after bounded recovery or process termination. No background delivery guarantee is
claimed. Existing PKCE wall-clock age and custom-scheme ownership findings remain deferred.
No attendance mutations, emulator, proof capture, Vue/iOS changes, hosted changes, commit
or push are part of this phase.

# U7.5D.1 — Secure read-only attendance integration

Baseline: `96460d16be43364b8fc81e7398ec86d816dc3600`, `main`, clean mobile worktree;
origin `https://github.com/Ralphwasnotfound/ojt-dtr-mobile-widgets.git`.
Changes are Android-only, unstaged and uncommitted.

## Contract and scope

Inspected the active Vue `supabaseAttendance.js`, proof-backed attendance service,
and S1/U3/U4.1/U4.2 migrations. The client calls only `attendance_summary()` with
no student identifier and SELECTs the authenticated student's own profile columns
`id,role,status,required_hours`. No attendance mutation, proof upload, camera,
location, widget, worker, new auth client/session, or persisted attendance cache.
Hosted migration deployment is not assumed or checked. Missing RPC/schema-cache
contracts and HTTP 404 are unavailable; SQL 42501 and HTTP 401/403 fail closed.
SDK error descriptions/bodies never enter presentation state or logging.

`AttendanceContract` checks one response row, required fields, JSON primitive types,
UUIDs, dates/timestamps, null relationships, action eligibility, session ownership,
ordinals/order/non-overlap, counts, and nonnegative finite decimal durations. Required
hours must be a positive bounded integer from an approved student profile. Unknown
fields are ignored, never copied into presentation state. No absent/malformed field
receives a synthetic zero. Decimal server totals are preserved with BigDecimal;
remaining seconds are clamped at zero. Today's closed-session total is cross-checked
against its server timestamps. Open sessions never add running time to completed hours.

Calendar semantics use Asia/Manila. Entire closed overnight durations belong to the
start day, matching SQL. A prior-day open session is represented separately from
`today_sessions` and remains IN. With two sessions, the latest is shown; this phase
is a summary, not a full session/history UI.

## Session and state boundary

`AuthCoordinator` alone holds the SDK client, session, user and generation binding.
Each attendance request verifies that binding before I/O, between profile and RPC,
and after RPC, including current SDK session identity, token equality, expiry,
Authenticated status and approved application state. Profile denial is checked before
the RPC. No tokens/client/binding objects are exposed through attendance state.

Every authorization withdrawal, profile refresh, logout or client/session replacement
clears the binding and memory cache and cancels the request. The repository additionally
checks binding object identity, request revision and current session validity before
success or stale fallback, so delayed non-cooperative results
or errors cannot overwrite replacement data. Existing SDK storage leases, session
observer, PKCE cleanup and epoch protections are preserved.

The repository is a testable Main-dispatcher state holder, not a separately owned
Android ViewModel. It exposes AccountChanged, Loading, Fresh, Stale, AccessDenied and
Unavailable. An initial network failure is unavailable. A later network failure may
retain only the same binding's explicitly stale snapshot; denied, malformed or missing
contracts clear it. Nothing in this cache authorizes actions. Cancellation propagates;
a bounded 15-second timeout is a read/network failure.

## Companion UI and freshness

Only the approved student branch renders attendance. Displays validated IN/OUT,
latest/open timestamps, Philippine attendance day, today/all-time completed hours,
required/remaining hours and confirmation time. Loading/denial/unavailable/stale states
are explicit. No native Time In/Out buttons exist. The UI refreshes on approved entry,
app resume, manual refresh and the next Philippine midnight. The daily timer is a
sleep until the boundary, not a busy loop; resume refetches after process suspension.
No background freshness or immediate remote-revocation notification is promised.

Freshness means an accepted read for the current binding/day, not continuous live
monitoring. Network failures do not reveal whether an unseen account revocation has
occurred. Profile/RPC checks enforce server access on each successful read; session
invalidation and locally observed account withdrawal immediately clear display data.
Profile and summary are separate requests, not an atomic backend snapshot. Device
clock differences can conservatively label an otherwise valid server-day snapshot stale.

## U7.5D.1.1 — Review correction and physical Samsung verification

The baseline and all twelve U7.5D.1 changed/new paths were verified and preserved.
Corrections affect AttendanceSummary.kt, AttendanceTest.kt, AuthCoordinator.kt,
AuthCoordinatorTest.kt and this document only.

SQL derives completed_sessions from every row with a Time Out and days_present
from distinct Time In dates in Asia/Manila. The unique open-session index permits
at most one remaining row. Thus rowCount = completed_sessions + (open ? 1 : 0),
days_present is zero exactly when rowCount is zero, and both days_present and
starts_today cannot exceed rowCount. BigInteger avoids overflow at extreme counts.
No historical maximum of two rows per day is inferred from these aggregate SQL
expressions. Positive tests preserve empty histories, same-day multiple rows,
open/overnight sessions and extreme counts; negative tests reject impossible days.

The corrected SDK logout test validates a recognizable 2700.25-second today /
9000.25-second all-time fixture before use. It blocks the mock response until after
logout, observes actual response construction, then joins the coordinator attendance
job through an internal completion-only barrier before asserting no late publication.
No SDK client, credentials, result or mutable job is exposed to UI. SDK fencing is
unchanged; the test passed on physical hardware.
